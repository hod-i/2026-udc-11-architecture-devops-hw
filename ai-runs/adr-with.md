  - П7. API кур'єра ідемпотентний за parcel_id, тобто повторний запит на

  - П8. Worker працює в одному екземплярі. Рішення лишається коректним і при

  Decision

  Кожну майбутню дію щодо посилки зберігаємо як рядок у новій таблиці
  parcel_tasks у PostgreSQL. Рядки створюються в тій самій транзакції, що й
  посилка. Наявний контейнер worker періодично забирає задачі, чий час настав, і
  виконує їх з гарантією «не більше одного разу» для SMS та «принаймні один
  раз» для запиту кур'єру. Нічний cron повернення прибираємо.

  1. Модель даних

  CREATE TABLE parcel_tasks (
    id           bigserial   PRIMARY KEY,
    parcel_id    bigint      NOT NULL REFERENCES parcels(id),
    kind         text        NOT NULL,  -- sms_arrival | sms_remind_24h |
  sms_remind_48h
                                        -- | return_to_sender | courier_return
    priority     smallint    NOT NULL,  -- 0 return/courier, 1 arrival, 2
  reminders
    due_at       timestamptz NOT NULL,
    state        text        NOT NULL DEFAULT 'pending',
                 -- pending → claimed → sending → done
                 -- + cancelled | uncertain | failed
    attempts     int         NOT NULL DEFAULT 0,
    locked_until timestamptz,
    provider_ref text,                  -- id SMS від провайдера / відповідь
  кур'єра
    last_error   text,
    UNIQUE (parcel_id, kind)            -- структурна гарантія: одне
  повідомлення кожного виду
  );
  CREATE INDEX parcel_tasks_due ON parcel_tasks (priority, due_at) WHERE state =
  'pending';

  Телефон і код у цій таблиці не дублюються: їх беремо з parcels через JOIN у
  момент надсилання. Так їх менше копіюється, а все лишається на VM у
  Франкфурті.

  2. Створення задач

  registerParcel в одній транзакції вставляє посилку і чотири задачі:
  - sms_arrival з часом «зараз»;
  - sms_remind_24h з часом arrivedAt + 24h;
  - sms_remind_48h з часом arrivedAt + 48h;
  - return_to_sender з часом arrivedAt + 72h.

  Якщо час SMS-задачі припадає на 21:00–08:00 за Києвом, його одразу зсуваємо на
  найближчі 08:00. Нагадування через 48 год вмикається прапорцем
  REMINDER_48H_ENABLED, тож його можна «відрізати», як дозволяє бриф, без змін у
  коді. До pool додаємо withTransaction(fn), а в in-memory сховищі робимо його
  емуляцію для тестів.

  3. Обробка: два незалежні цикли в процесі worker

  - Цикл повернень (кожні 10 с) обробляє return_to_sender і courier_return. Він
    не чекає на розсилку SMS, тож повернення стається протягом приблизно 10–15 с
    після дедлайну.
  - Цикл SMS (кожні 10 с, а при повному пакеті одразу знову, як зараз) обробляє
    sms_*. SMS про прибуття йдуть першими (priority), нагадування пізніше. Пакет
    вивантаження з 300 посилок і нагадування, що збіглися з ним у часі,
    розходяться за кілька хвилин.

  Задачі забираються так:
  UPDATE parcel_tasks SET state='claimed', attempts=attempts+1,
  locked_until=now()+interval '2 min'
   WHERE id IN (SELECT id FROM parcel_tasks
                 WHERE state='pending' AND due_at<=now() AND kind = ANY($kinds)
                 ORDER BY priority, due_at LIMIT 50
                 FOR UPDATE SKIP LOCKED)
  RETURNING *;

  4. SMS: спершу запис, потім надсилання

  Для кожного SMS виконуємо послідовно:
  1. Перевірка тихих годин за Europe/Kyiv через Intl, а не через TZ контейнера.
     Якщо зараз ніч або до 21:00 лишилось менше 30 с, повертаємо задачу в
     pending з часом 08:00.
  2. Атомарно позначаємо задачу як sending, лише якщо посилка ще чекає:
     UPDATE parcel_tasks SET state='sending' WHERE id=$1 AND state='claimed' AND
     EXISTS (SELECT 1 FROM parcels WHERE id=$parcel AND status='waiting').
     Якщо оновилося 0 рядків, посилку вже забрали або повернули, і задача стає
     cancelled. Якщо цей запис не вдався, SMS не надсилається. Отже, SMS ніколи
     не йде без запису в базі.
  3. Надсилаємо. Результат обробляємо так:

  ┌────────────────────────────┬──────────────────────┬─────────────────────┐
  │         Результат          │      Що означає      │         Дія         │
  ├────────────────────────────┼──────────────────────┼─────────────────────┤
  │ 2xx                        │ надіслано            │ done, provider_ref  │
  │                            │                      │ = id провайдера     │
  ├────────────────────────────┼──────────────────────┼─────────────────────┤
  │ 429                        │ провайдер гарантує,  │ pending, due_at =   │
  │                            │ що не надіслано      │ now + Retry-After   │
  ├────────────────────────────┼──────────────────────┼─────────────────────┤
  │ мережева помилка до        │                      │ pending з           │
  │ відправки запиту (DNS,     │ точно не надіслано   │ експоненційною      │
  │ ECONNREFUSED)              │                      │ затримкою           │
  ├────────────────────────────┼──────────────────────┼─────────────────────┤
  │ інша 4xx (наприклад,       │ не надсилатиметься   │ failed, алерт       │
  │ хибний номер)              │                      │                     │
  ├────────────────────────────┼──────────────────────┼─────────────────────┤
  │ 5xx, тайм-аут після        │                      │                     │
  │ відправки, падіння процесу │ невідомо             │ uncertain           │
  │  в стані sending           │                      │                     │
  └────────────────────────────┴──────────────────────┴─────────────────────┘

  4. Політика для uncertain — це свідомий компроміс, бо провайдер не дає ключа
     ідемпотентності:
     - sms_arrival: через 5 хв один повтор з іншим текстом («Повторно: посилка
       чекає у поштоматі №12. Код: 123456») і алерт. Втратити код гірше, а
       позначене «Повторно» SMS не виглядає як шахрайство.
     - нагадування: не повторюємо, ставимо failed. Пропущене нагадування коштує
       менше, ніж дубль.
  5. Відновлення після падіння. Задачі в claimed з простроченою locked_until
     повертаються в pending, бо їх гарантовано не надсилали. Задачі в sending з
     простроченою locked_until переходять у uncertain.
  6. Якщо через простій одночасно настав час нагадувань через 24 і 48 год,
     надсилаємо лише друге.

  Тексти мають вкладатися в 70 символів, тобто в один сегмент. Приклад
  нагадування: «Нагадування: посилка у поштоматі №12, код 123456, до 01.11
  14:05» (64 символи). Остаточні тексти погоджують Олена і комунікаційна
  команда, формулювання «посилка чекає» погоджене юристкою. У sms.js треба
  врахувати Retry-After і підняти швидкість до 8/с: це запас 20 % до ліміту
  10/с.

  5. Повернення через 72 години: одна транзакція

  BEGIN;
  UPDATE parcels SET status='returned', returned_at=now()
   WHERE id=$1 AND status='waiting' RETURNING id;      -- 0 рядків → вже забрали
  → задача cancelled
  INSERT INTO events (parcel_id, type, at) VALUES ($1, 'returned', now());
  UPDATE parcel_tasks SET state='cancelled'
   WHERE parcel_id=$1 AND kind LIKE 'sms_%' AND state IN ('pending','claimed');
  INSERT INTO parcel_tasks (parcel_id, kind, priority, due_at)
   VALUES ($1, 'courier_return', 0, now()) ON CONFLICT DO NOTHING;   -- outbox
  для кур'єра
  UPDATE parcel_tasks SET state='done' WHERE id=$task;
  COMMIT;
  З моменту COMMIT код недійсний. courier_return викликає API кур'єра і повторює
  спроби з експоненційною затримкою до 24 год (спирається на П7). Після 5
  невдач приходить алерт у #poshtomat-oncall. Так нинішня вада «повернено, але
  кур'єр не знає» стає неможливою.

  6. Видача стає атомарною

  pickup переходить на одне умовне оновлення:
  UPDATE parcels SET status='picked_up', picked_up_at=now() WHERE code=$1 AND
  status='waiting' RETURNING id, locker_id.
  Повернення і видача використовують ту саму умову status='waiting', тож виграє
  рівно одна з них.

  7. Вікно резервного копіювання 02:00–02:30

  Worker виставляє lock_timeout = 5s. Транзакції повернення в цьому вікні
  падають і повторюються на наступному циклі, тож затримка не перевищує 30 хв.
  SMS у цей час і так не надсилаються через тихі години. Алерт «прострочена
  задача» в цьому вікні не спрацьовує.

  8. Що прибираємо і як мігруємо

  - Прибираємо cron-рядок о 03:15 і файл bin/expire-parcels.js.
  - Посилки, які вже чекають, переносимо одним скриптом:
    - sms_arrival створюємо як done, якщо notifiedAt заповнене, інакше як
      pending;
    - нагадування створюємо лише ті, чий час ще не настав, щоб не розсилати
      застарілі;
    - return_to_sender ставимо на arrivedAt + 72h. Прострочені посилки
      повернуться одразу, тому деплой робимо в будній день удень, коли працює
      гаряча лінія.
  - Виправляємо app/docs/ARCHITECTURE.md за кодом.
  - Додаємо пункт у runbook відновлення. Після pg_restore і до запуску worker
    SMS-задачі в pending, чий час між моментом дампу і моментом відновлення,
    переводимо в uncertain і переглядаємо вручну. Інакше відновлення вчорашньої
    копії розішле людям SMS повторно.

  9. Спостережуваність

  - Метрики: найстаріша прострочена задача (pending з due_at < now() − 5 min,
    поза тихими годинами і вікном бекапу), кількість uncertain і failed, помилки
    кур'єра. Усі вони мають алерти в #poshtomat-oncall.
  - Heartbeat worker: час останнього успішного циклу.
  - Кількість SMS за добу за видами, для звіту в бюджет комунікацій.
  - У логах лише parcel_id, kind, state, без телефонів і кодів (як зараз).
  - Виконані задачі старші за 90 днів видаляємо. Це припущення щодо строку
    зберігання, його треба погодити з DPO.

  ---

  Розглянуті альтернативи

  Б. Черга з відкладеними задачами на VM (Redis + BullMQ або RabbitMQ з
  delayed-exchange)

  - Плюси: точність таймерів до мілісекунд, готові повтори і backoff, push
    замість опитування. Масштабується на тисячі задач за секунду.
  - Мінуси:
    - Новий stateful-сервіс, який двоє людей мусять налаштувати
      (AOF/persistence), бекапити, моніторити й відновлювати.
    - Пам'ять на VM з 4 GB.
    - Перша npm-залежність у проєкті, який зараз має нуль залежностей.
    - Проблема подвійного запису: посилку в базі закомічено, а задача в черзі не
      створилась, або навпаки. Щоб це закрити, однаково потрібен outbox у
      PostgreSQL, тобто фактично рішення А плюс Redis.
    - Скасування після видачі вимагає або видаляти відкладені задачі, або
      перевіряти статус під час виконання.
    - Телефон опиниться в черзі, якщо не передавати лише parcel_id. Дані
      лишаються в ЄС, але ще одне місце для аудиту.
  - Вартість: 0 € на інфраструктуру.
  - Коли варто переглянути: якщо обсяг зросте на порядки або з'являться інші
    сервіси-споживачі.

  В. Керований хмарний планувальник (AWS EventBridge Scheduler в eu-central-1
  або Google Cloud Tasks у europe-west3), який викликає наш HTTP-ендпоїнт

  - Плюси: таймери поза нашою VM, переживають навіть її падіння. Точність
    близько хвилини. Ціна — кілька центів на місяць, у межах 60 €. Простий SQS
    не підходить: його максимальна затримка 15 хв.
  - Мінуси:
    - Новий постачальник: договір, DPA, перевірка регіону для комплаєнсу, нова
      стаття у звіті за грантом.
    - Публічний автентифікований ендпоїнт для вхідних викликів, тобто нова
      поверхня атаки.
    - Той самий подвійний запис.
    - Збій у хмарі зупиняє наші таймери, і ми на це не впливаємо.
    - Немає локального запуску для npm test.
    - Новий інструмент для двох людей і для чергових.

  Г. Cron щохвилини замість нічного запуску (* * * * * docker compose run --rm
  worker npm run tick)

  - Плюси: звичний для команди інструмент і мінімальні зміни у способі запуску.
  - Мінуси:
    - Старт контейнера щохвилини на 2 vCPU.
    - Запуски можуть перекриватися, тож потрібні flock або advisory lock.
    - Точність 1 хв плюс час старту.
    - Головне: проблеми дублів і втрат не зникають. Модель задач і стани з А
      однаково потрібні, тож це А з гіршим способом запуску. Модель даних А
      дозволяє перейти на цей варіант, якщо колись знадобиться.

  Д. Таймери в пам'яті процесу (setTimeout на кожну посилку)

  Відкинуто одразу: перезапуск губить таймери. Саме це сталося взимку.

  Consequences

  Що стає краще

  - Повернення відбувається протягом секунд після 72 год, а не через 3–4 доби.
    Комірки звільняються в середньому на 1–2 доби раніше.
  - Таймери зберігаються в базі, тож переживають перезапуски і деплої, і
    потрапляють у нічні бекапи.
  - Дубль того самого повідомлення неможливий структурно: UNIQUE, запис стану
    перед надсиланням, 429 не повторюється наосліп. Рідкісний випадок «невідомо»
    дає одне позначене повторне SMS лише для коду.
  - Попутно виправляються три наявні вади: порядок «повернено → кур'єр», гонка
    видачі й повернення, ігнорування Retry-After.
  - Без нових витрат на ІТ і без нових технологій для команди. Нагадування через
    48 год вмикається одним прапорцем.

  Що стає гірше або ризиковано

  - Worker стає критичним компонентом. Якщо він стоїть, зупиняються і SMS, і
    повернення. Від цього захищають алерти на heartbeat і на прострочені задачі,
    але чергує одна людина, а гаряча лінія у вихідні не працює.
  - Гарантувати рівно одну доставку неможливо, бо провайдер не дає ключа
    ідемпотентності. Лишається залишковий ризик: одне SMS «Повторно» після збою
    під час надсилання, або зрідка втрачене нагадування. Ми свідомо обрали такий
    компроміс.
  - «Одразу» не діє вночі. Посилка, зареєстрована о 22:00, отримає SMS о 08:00.
    Якщо рахувати 72 год від реєстрації (П2), у людини фактично лишається до ~61
    год.
  - Вікно бекапу затримує повернення до 30 хв. Видача о 02:00–02:30 і зараз
    падає на записі, але це окрема наявна проблема.
  - Постійне опитування бази кожні 10 с по частковому індексу. Навантаження на
    нашому масштабі незначне.
  - Відновлення з бекапу вимагає нового ручного кроку (див. п. 8 рішення),
    інакше люди отримають повторні SMS.
  - Більше SMS — більші витрати з бюджету комунікацій. На кожні 1000 посилок,
    якщо 30 % не заберуть за 24 год і 10 % за 48 год, це +400 SMS ≈ +14 €. Обсяг
    посилок за місяць у матеріалах не наведено, тож суму треба порахувати разом
    з Іриною.
  - Обсяг роботи: транзакції в шарі даних, нова таблиця, переписаний worker,
    міграція, тести з підробленим годинником (тихі години, перехід на зимовий
    час, гонка видачі й повернення, збій на кожному кроці).

  Рекомендації поза межами цього ADR

  - Андрію варто перевірити, чи потрібне блокування запису під час бекапу.
    pg_dump знімає узгоджений знімок без блокування записів. Якщо прибрати
    блокування, зникне і 30-хвилинна затримка повернень, і падіння видачі вночі.

  Відкриті питання (до впровадження)

  1. Ірина / юристка. Рахуємо 72 год від реєстрації посилки чи від першого SMS?
     Для нічних посилок різниця до 11 год.
  2. Ірина / комунікаційна команда. Чи погоджуєтесь, що нагадування містять код
     (П5)? Без коду нагадування не допоможе тим, хто видалив перше SMS.
  3. Служба доставки. Чи ідемпотентний returns API за parcel_id (П7)? Як і коли
     кур'єр фізично звільняє комірку? Що саме бачить відправник (П3, П4)?
  4. DPO / провайдер SMS. Де обробляються номери телефонів у провайдера (П6)?
     Потрібне письмове підтвердження обробки в ЄС.
  5. Бюджет комунікацій. Підтвердити додаткові витрати на нагадування за
     реальним місячним обсягом посилок.
